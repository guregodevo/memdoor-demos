### NOTES

The core difficulty is answering up to 200,000 queries asking for the largest "400 number" at most A, where A goes up to 10^12. A 400 number is N = p^(2a)·q^(2b) for distinct primes p, q and positive integers a, b. The critical structural insight is that every 400 number is a perfect square: N = (p^a·q^b)^2, so N = m^2 where m has exactly two distinct prime factors. Since N ≤ 10^12, we have m ≤ 10^6, which is small enough for a linear sieve or simple factor-counting pass.

The main tension is between precomputation cost (building a global structure over all valid m up to 10^6) and per-query cost (how fast can we answer "what is the largest 400 number ≤ A?"). With Q up to 200,000, even a per-query cost of a few hundred operations is fine, but a per-query cost of millions is not.

A subtle pitfall in any approach: computing floor(sqrt(A)) for A up to 10^12 must be done with integer square root (math.isqrt) to avoid floating-point rounding errors that could off-by-one the candidate m.

Another pitfall: the problem states "exactly 2 distinct prime factors" and "each appears with an even exponent ≥ 2." This means m must have at least one of each prime, so the smallest valid m is 2·3 = 6, giving 36 as the smallest 400 number. Any approach must correctly exclude m values that have 0, 1, 3, or more distinct prime factors, and must not include m = 1 or prime powers.

### NEXT

- **Approach A – Pair-and-exponent enumeration:** Sieve all primes up to 10^6. Iterate over every unordered pair of distinct primes (p, q) with p < q and p·q ≤ 10^6 (this constraint alone bounds the outer loop to primes p below 1000, since p < q implies p² < p·q ≤ 10^6). For each pair, iterate a from 1 upward while p^(2a)·q^2 ≤ 10^12, and for each a iterate b from 1 upward while p^(2a)·q^(2b) ≤ 10^12, collecting the product into a list. Sort and deduplicate (dedup is actually unnecessary since unique factorization guarantees no duplicates). Answer queries with bisect_right. Pitfall: the inner loops must break early to stay fast; also must not accidentally include p = q.

- **Approach B – Omega-sieve plus sorted list of squares:** Run a linear (or standard) sieve up to 10^6 to compute omega(n), the number of distinct prime factors of each n. Collect every m in [1, 10^6] with omega(m) == 2, compute m² for each, sort the resulting list of roughly 350,000–400,000 squares. For each query, use math.isqrt(A) to get the upper bound on m, then bisect_right into the sorted list of squares (or equivalently bisect on m and square). Pitfall: the sieve must count *distinct* prime factors, not total prime factors with multiplicity; a naive "divide out p fully" sieve works, but a linear sieve tracking a flag per prime also works.

- **Approach C – Omega-sieve plus per-query downward scan in m-space:** Same omega sieve up to 10^6. For each query, compute m_max = math.isqrt(A), then check m_max, m_max - 1, m_max - 2, … until finding the first m with omega(m) == 2; the answer is m². The gap between consecutive integers with exactly two distinct prime factors is small in practice (typically 1–5, worst case up to perhaps 30–50 for m ≤ 10^6), so this is O(gap) per query. Pitfall: one must verify empirically (or by reasoning) that the maximum gap up to 10^6 is small enough that 200,000 × max_gap stays well within the time limit in Python. If the gap could be a few hundred, this still works (200,000 × 500 = 10^8 simple array lookups), but it is less clean than a binary search.

- **Approach D – Omega-sieve plus "previous qualifying m" lookup table:** Same omega sieve. Build an auxiliary array prev[m] = largest m' ≤ m with omega(m') == 2 (for m < 6, prev[m] = sentinel). Each query then becomes: m = prev[math.isqrt(A)]; answer = m * m. This is O(1) per query after an O(10^6) precomputation. Pitfall: the lookup table is 10^6 integers, about 8 MB of memory, which is fine. Must handle the sentinel case (though the problem guarantees a 400 number ≤ A always exists for A ≥ 36, so m ≥ 6 is guaranteed to have a qualifying predecessor).

- **Approach E – Precompute squares and use a binary search on m directly:** Instead of storing the list of squares, store the sorted list of qualifying m values (those with omega(m) == 2, i.e., roughly 370,000 integers up to 10^6). For each query, bisect_right on the m-list with key m_max = math.isqrt(A), take the element at index-1, and return its square. This avoids storing 64-bit squares and keeps the list smaller in memory. Pitfall: essentially identical to Approach B but the bisect target is m_max rather than A; must be careful that we are bisecting on m, not on m².
