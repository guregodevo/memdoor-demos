### NOTES

**Core Difficulty:** The problem reduces to determining whether a set of people contains a "conflicting pair." After establishing that a person going from a to b (a < b) imposes the constraints P_{a-1} = P_{b-1} and (strictly) P_k > P_{a-1} [right-going] or P_k < P_{a-1} [left-going] for all interior prefix-sum indices k, one can verify that infeasibility of a set is equivalent to the existence of a conflicting pair: (i) two same-direction people whose intervals [l_i, r_i] and [l_j, r_j] (where l = min(S,T)-1, r = max(S,T)-1) "properly cross" — meaning max(l_i,l_j) < min(r_i,r_j) but neither interval contains the other — or (ii) two opposite-direction people sharing either their left or right endpoint. Pairwise conflicts are both necessary and sufficient: same-direction non-conflicting intervals form a laminar family (assignable by nesting depth), and the absence of shared endpoints between opposite-direction people prevents 2-cycles in the constraint graph. Longer cycles cannot arise without a pair conflict due to the directional structure of the inequality edges (right-going edges always point "toward the base," left-going always "away from the base").

Given the pairwise characterization, each query [L,R] asks: does there exist a conflicting pair (i,j) with L ≤ i < j ≤ R? The standard reduction is: for each j compute prev[j] = max{i < j : (i,j) conflicts}, then answer "No" iff max(prev[L+1..R]) ≥ L (and "Yes" if L=R). This leaves two sub-problems: computing prev[] efficiently, and answering range-max queries on it.

The hard sub-problem is computing prev[j] for the crossing case. For a right-going person j with interval [l_j, r_j], crossing predecessors are: (A) right-going i with l_i < l_j and r_i ∈ (l_j, r_j), and (B) right-going i with r_i > r_j and l_i ∈ (l_j, r_j). This is a 2D orthogonal range-max query (maximize i over a rectangle in the (l,r) plane) with the additional constraint i < j, making it a 3D offline query naturally solved by CDQ divide-and-conquer on the index dimension, with a sweep-line + segment tree handling the 2D part at each cross-step.

**Shared-endpoint conflicts** (same-direction or opposite-direction) are straightforward: maintain "last seen" arrays indexed by endpoint value, updated in a single left-to-right pass.

**Pitfalls identified:**
- Strict vs. non-strict inequality at interval boundaries (crossing requires strict overlap of interiors; touching intervals are NOT conflicts).
- The CDQ must guarantee i < j via the left/right half split; the spatial sweep within a cross-step must use strict inequalities matching the crossing definition.
- The segment tree must be reset between cross-steps (or use a "touched positions" list for partial reset).
- Running the CDQ separately for right-going and left-going subsets (crossing only applies within the same direction).
- Python speed: ~70M+ basic operations from the CDQ may be near the time limit; iterative (non-recursive) implementations and pre-allocated arrays are important.
- The prefix-sum index l = a-1 can be 0 (when a=1), so the segment tree range is [0, N-1].

### NEXT

- **Approach 1 (CDQ + iterative segment tree):** Run CDQ divide-and-conquer on index [1, M] separately for right-going and left-going people. At each cross-step, handle type-A crossings (l_i < l_j < r_i < r_j) via an ascending-l sweep with a segment tree over r (point-update max index, range-max query over (l_j, r_j)), and type-B crossings (l_j < l_i < r_j < r_i) via a descending-r sweep with a segment tree over l. Combine with O(M) shared-endpoint detection. Build a sparse table over prev[] for O(1) query answering. Total O(M log M log N + M log M + Q).
- **Approach 2 (2D Fenwick tree / range tree, no CDQ):** Build a 2D offline data structure: a BIT over the l-coordinate where each node stores a sorted list of r-values and a corresponding BIT for max-index. Preprocess all right-going (and left-going) points. For each j in index order, query the 2D structure for max i with l_i < l_j and r_i in (l_j, r_j) (type A), and separately for r_i > r_j and l_i in (l_j, r_j) (type B). Total O(M log²N). Slightly worse asymptotic but avoids CDQ recursion; may have better Python constants due to simpler control flow.
- **Approach 3 (Sweep-line with sorted-list + "last max" trick):** For type A only: sort all right-going people by l. Process queries (also sorted by l_j) with a pointer adding points to a 1D segment tree over r. The "i < j" constraint is handled by processing people in index order and using a BIT that stores the max index at each r-position (so the answer to a range-max query is automatically the max index among all inserted points, and since we insert in index order, all inserted points have index ≤ current). Wait — this only works if insertion order matches index order, which it does NOT when sweeping by l. So this approach requires the CDQ to reconcile the two orderings. Abandon unless combined with CDQ (reduces to Approach 1).
- **Approach 4 (Offline 3D dominance via divide-and-conquer on value):** Binary-search the answer for each j (the max conflicting i). For a given midpoint m, check "is there any conflicting i in [m, j-1]?" using a 2D sweep. This gives O(M log M log²N) — worse than Approach 1 and more complex. Not recommended.
- **Approach 5 (Hybrid: O(M√M) bucket method):** Partition indices into blocks of size B ≈ √M. For each block, precompute which people in the block conflict with each person outside. For a query [L,R], check intra-block conflicts via precomputation and inter-block via a sweep. Total O(M√M + Q√M). Simpler to implement but O(M√M) ≈ 9×10^7 may be too slow in Python and doesn't obviously improve on CDQ.

**Recommended next step:** Implement Approach 1 (CDQ + iterative segment tree) with careful attention to strict inequality boundaries, separate right/left CDQ runs, and an iterative (bottom-up) segment tree to minimize Python overhead. Validate on both samples, then stress-test with a brute-force O(M²) checker on small random inputs.
