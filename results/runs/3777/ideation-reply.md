### NOTES

The core difficulty is that we must simultaneously track two quantities (alternating sum and product) under two constraints (sum must equal k, product must not exceed limit), and the "maximize product" objective interacts non-trivially with the "product ≤ limit" constraint. Specifically, a smaller intermediate product for the same (sum, parity) state can sometimes lead to a better final answer than a larger one, because the larger product may be unable to absorb further multiplications without exceeding the limit, while the smaller product can. For example, with limit=5000, products 1000 and 1 in the same state: multiplying by remaining [12,12,12] gives 1000 stuck (1000·12>5000) vs. 1→12→144→1728, and 1728>1000. This kills the naive "keep only max product per state" DP.

The sum dimension is bounded: with n≤150 and values 0..12, the alternating sum ranges over at most [−1800, +1800]. The product dimension is bounded by limit≤5000. The 0/1 nature of subsequence selection means we process left-to-right with snapshot-based updates.

Key structural facts:
- All elements are non-negative (0 to 12), so products never decrease (they stay the same at ×0 or ×1, grow otherwise).
- The "parity" (whether the next appended element is added or subtracted) is determined by the current subsequence length mod 2.
- Starting a new subsequence with element x yields state (sum=x, parity=1, product=x).
- Element 0 creates product 0, which is a valid (but minimal) product. We must distinguish "reachable with product 0" from "unreachable."

The main algorithmic tension is between the number of (sum, parity) states (~3600×2) and the number of distinct products per state (up to 5000 in the worst case, but typically far fewer in practice because products grow quickly and are capped at 5000).

### NEXT

- **Sparse set DP with dominance pruning:** Maintain a dictionary mapping (sum_offset, parity) to a set of achievable products (all ≤ limit). Process each element left-to-right: snapshot the dict, then for every (s,p)→prods in the snapshot, for every prod in prods, compute the "take" transition (new_s = s±x, new_p = 1−p, new_prod = prod·x) and insert into the live dict if new_prod ≤ limit. Also insert the "start new" transition (x, 1)→{x}. After processing element i (of n), prune each set: remove product p if p · 12^(n−i−1) ≤ max(set), because p can never outgrow the set's maximum even with all remaining elements at their max value. This keeps sets small. At the end, the answer is the max product in dp[(k,0)] ∪ dp[(k,1)] if non-empty, else −1 (with special handling for product=0 being a valid answer when the set is non-empty). Pitfall: the pruning bound 12^(remaining) is loose; a tighter bound using the actual remaining elements would prune more but costs more to compute. Also must handle the "start new" transition separately and ensure x=0 produces product 0 correctly.

- **Bitset-encoded product DP:** Represent the set of achievable products for each (sum, parity) as a Python big integer (bitset of 5001 bits, bit p set iff product p is reachable). Precompute for each x∈{1,...,12} a lookup: given a bitset B, the result of "multiply all set bits by x and mask to ≤ limit" is R where bit (p·x) is set in R iff bit p is set in B and p·x≤limit. This multiplication-of-bitset operation can be implemented by iterating set bits (using bit_length and lowbit tricks) or by a precomputed table mapping 16-bit chunks. The DP then becomes: for each element x, for each (s,p), OR the multiplied bitset of dp[s][p] into dp[new_s][new_p]. Pitfall: the "multiply bitset by x" operation is not a simple shift; for x=1 it is identity, for x>1 it is a sparse permutation of bit positions. Implementing this efficiently in pure Python (no numpy) requires careful use of integer bit operations. The 5001-bit integers are ~625 bytes each, and we have ~7200 of them, so memory is fine. The per-element work is ~7200 bitset operations, each taking O(5000/x) bit manipulations.

- **Product-indexed DP with sum-tracking:** Reverse the roles: for each product value P (0 to limit), maintain a bitset (or set) of reachable (sum, parity) pairs. For element x, for each P with non-empty state set, compute P·x and if ≤ limit, merge the (shifted) sum states. The "start new" transition adds (x, 1) to the state set for product x. At the end, scan products from limit down to 0, and for each P check if (k, 0) or (k, 1) is in its state set; return the first (largest) P found, or −1. Pitfall: the number of non-zero product values that actually appear may be large (up to ~2000 distinct values ≤ 5000 with prime factors in {2,3,5,7,11}), and for each we iterate over potentially many (sum, parity) pairs. Also, product 0 is a special case (any subsequence containing a zero has product 0, and there may be many such subsequences with different sums).

- **Two-phase approach: first find reachable (sum, parity) states, then optimize product:** Phase 1: run a boolean DP (no product tracking) to determine which (sum, parity) states are reachable at all. This gives the set of valid target states. Phase 2: for the specific target k, do a backward DP or a constrained search that tracks only the product, starting from the end and working backward, to find the maximum product ≤ limit achievable for state (k, 0) or (k, 1). This reduces the product-tracking to only the states on "paths to k." Pitfall: identifying which intermediate states lie on a path to (k, ·) requires backward reachability, which adds a second full DP pass. The backward DP would track (sum, parity) → set of products, but only for states that can reach (k, ·) in the remaining suffix, which requires the forward pass first.

- **Group-by-value optimization:** Since element values are only 0..12, process all occurrences of value v together rather than one-by-one. For value v, the "take" transition multiplies the product by v and shifts the sum by ±v. Multiple takes of the same value v correspond to multiplying by v^m and shifting sum by ±v·m. We can precompute the effect of taking m copies (for m=0,1,2,...) and apply them in batch. Pitfall: the 0/1 constraint means each occurrence is distinct; we cannot simply "take m copies" without tracking which positions were used. However, since all copies of value v are interchangeable (same contribution to sum and product), we can treat them as a bounded-knapsack item with count c_v, reducing the per-value work. This only helps if many elements share the same value.
